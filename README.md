# git-init

`git-init` is a contract-driven, Copier-based project template for starting
open-source software projects.

It provides a stable software-development lifecycle baseline without requiring
a programming language, application framework, cloud provider, or deployment
platform. Projects begin with the core contract and add capability stages as
they mature.

## Current implementation

The repository currently provides:

- the repository contract in [`spec/`](spec/);
- a minimal Copier template configured through [`copier.yml`](copier.yml);
- generated project metadata and governance files;
- a core `Taskfile.yml` with technology-neutral checks;
- the current deployment book as reference material in [`book/`](book/).

The documentation, application, infrastructure, Kubernetes, Argo CD, and
observability stages are planned extensions. They are not generated by the
core template yet.

## Purpose

The stable part of a generated project is its lifecycle and governance:

- requirements, scope, and project planning;
- architecture, design documentation, and decision records;
- implementation and contributor workflows;
- automated quality, testing, and security checks;
- documentation for users, contributors, and operators;
- packaging, versioning, releases, and publishing;
- deployment, environments, migrations, and rollback;
- observability, incident response, maintenance, and improvement.

The implementation details remain configurable through project kinds,
technology profiles, and capability stages.

## Generation model

Copier is the generation and update engine. The repository contract is the
source of truth; Copier renders it and records the selected answers.

The first generation workflow is:

```bash
uvx copier copy \
  gh:sean-njela/git-init \
  ./my-project \
  --vcs-ref <tag-or-commit>
```

Generated projects record their template answers in `.copier-answers.yml` and
their active contract capabilities in `.project/project.yaml`.

## Capability stages

Projects may add capabilities incrementally:

- `docs` — MkDocs documentation and publishing;
- `automation` — Taskfile, toolchain, hooks, and CI;
- `application` — product source and tests;
- `container` — container packaging and supply chain;
- `release` — versioning, artifacts, and publishing;
- `terraform` — infrastructure provisioning;
- `ansible` — machine and system configuration;
- `kubernetes` — Kubernetes workloads and policies;
- `argocd` — GitOps reconciliation;
- `observability` — metrics, logs, dashboards, alerts, and runbooks.

No stage is enabled merely because it exists in the roadmap.

## GitHub-first operating model

GitHub is the default collaboration and automation platform:

- GitHub Actions for CI/CD and reusable automation;
- GitHub Issues, Projects, and pull requests for collaboration;
- GitHub security automation for dependency, code, and secret checks;
- GitHub Releases and Packages for distribution;
- GitHub Pages with MkDocs for project documentation.

External DevOps systems are explicit integrations. Kubernetes, Argo CD, and
cloud-specific controllers must extend the baseline rather than redefine it.

## Technology-neutral design

The template does not require Python, JavaScript, Django, Rails, React, Vue,
Docker, Terraform, Kubernetes, or any other specific stack. Stack-specific
behavior belongs in profiles and capability stages.

The default application source root is `src/`, but a profile may declare a
native layout such as `cmd/`, `internal/`, `packages/`, or another explicit
source root.

## Repository contract

The authoritative contract is
[`spec/000_repository-contract.md`](spec/000_repository-contract.md).
The generator contract is
[`spec/001_generator-contract.md`](spec/001_generator-contract.md).
The capability-stage contract is
[`spec/002_stage-contract.md`](spec/002_stage-contract.md).

Every normative specification contains front matter with a full Git commit SHA
identifying the revision against which it was reviewed.

## Reference material

[`book/`](book/) contains the current full-stack deployment and operations
reference. It is source material for future capability stages, not the final
generated-project contract. Its Python, Vue, Node, Nginx, Meilisearch, VM, and
provider-specific examples remain illustrative.
